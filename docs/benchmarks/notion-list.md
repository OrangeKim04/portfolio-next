# Notion 목록 조회 최적화 실측 (2026-10-20)

## 확인된 문제와 변경

- 기존 목록 서비스는 글 목록과 전체 개수를 별도의 Notion query로 조회했다.
- 요약 속성이 없는 글마다 blocks.children.list를 호출해 본문에서 요약을 생성했다.
- 운영 /blogs DOM에서 요약 10개 모두 computed display:none임을 확인했다. 홈은 요약을 렌더링하지 않는다.
- getPublishedPostPage가 한 번의 커서 순회에서 목록과 개수를 함께 생성한다. 두 결과를 한 캐시 항목에 저장하며 기존 60초 재검증 정책은 유지한다.
- 화면에서 사용하지 않는 자동 요약용 블록 요청을 제거했다. 명시적으로 저장된 Notion 요약 속성과 상세 본문 조회는 유지한다.
- 100개 초과 데이터는 next_cursor로 이어 조회한다. 전체 개수를 구하기 위해 모든 페이지를 읽는 구조이므로 데이터가 크게 늘면 별도의 개수 관리/인덱스가 필요하다.

## 측정 방법

- 기준 커밋: 45db9cad4a12491b58d4f9b365dac1eb53a792ef.
- scripts/benchmark-notion.cjs가 기준 커밋의 실제 서비스 코드를 git show로 읽고 현재 코드와 같은 프로세스에서 실행한다.
- 실제 연결된 Notion 데이터 22개 중 첫 페이지 10개, category 미지정.
- 전후 각 10회, 총 20회. 실행 순서를 쌍마다 뒤집고 각 샘플 사이 6초 휴지.
- 양쪽 모듈의 스키마/데이터 소스 메타데이터를 미리 로드했다. Next 데이터 캐시는 우회했다.
- SDK fetch 경계에서 실제 HTTP 요청과 비정상 상태 수를 계측했다. 재시도도 HTTP 요청 수에 포함한다.
- 같은 목록의 ID/slug/제목/카테고리/태그/작성자/게시일/읽기 시간/정렬 순서 및 전체 개수가 모든 실행에서 같은지 검증했다.
- 의도적으로 제거한 자동 요약과 만료되는 이미지 URL은 동등성 비교에서 제외했다. 썸네일 매핑 코드는 변경하지 않았다.
- 측정 범위는 Notion 서비스 함수다. DB 조회, tRPC 전송, HTML/JS 로딩, 브라우저 렌더링과 운영 서버의 캐시 적중 지연은 포함하지 않는다.
- 원문, Notion 식별자, 인증 토큰은 결과 JSON에 저장하지 않았다.

## 최종 실측

| 지표 | 기존 | 개선 |
| --- | ---: | ---: |
| 목록 조회당 실제 외부 HTTP 요청 | 12 | 1 |
| 데이터 소스 query 요청 | 2 | 1 |
| 요약용 본문 요청 | 10 | 0 |
| 조회 함수 중앙값 | 928.165ms | 335.55ms |

- 외부 요청 수 91.7% 감소.
- 이번 실행의 조회 함수 중앙값 63.8% 감소. 네트워크와 Notion 서버 상황에 따라 변하며 운영 성능 보장 수치는 아니다.
- p95는 표본 10개에서 사실상 최대값이므로 자기소개서의 대표 수치로 사용하지 않는다.
- 원본: notion-live.json.

## 중간 실험도 보존

notion-intermediate.json은 목록/개수 통합만 하고 요약 호출은 유지한 중간 실험이다. 1.5초 간격으로 측정했으며 개선안에서도 429 응답 8회와 재시도가 발생했다. 최종 결과와 혼합하지 않는다. 이 단계의 수치를 숨기거나 최종 개선 효과로 사용하지 않는다. 최종 실험은 양쪽 모두 6초 간격으로 변경했고 429가 없었다. 이 결과만으로 운영 rate limit 문제를 완전히 해결했다고 주장하지 않는다.

## 경계 검증

node scripts/benchmark-notion.cjs

- 0/25/100개 합성 데이터: 기존과 결과 일치, query 2회에서 1회.
- 125개 합성 데이터의 offset=100: 기존 total=100/반환 0개, 개선 total=125/반환 10개.
- 공개 상태와 카테고리 필터, 정렬 옵션이 각 커서 요청에 유지되는지 확인.
- 요약 없는 데이터에서 본문 조회 없이 null 반환, 저장된 요약은 보존.
- 합성 데이터 결과는 실제 서비스 장애 건수로 표현하지 않는다.

## 재현

node scripts/benchmark-notion.cjs --live

.env의 기존 NOTION_TOKEN과 NOTION_DATABASE_ID를 사용하며 읽기만 수행한다. 최종 측정 JSON을 덮어쓰므로 비교 기록이 필요하면 이전 결과를 별도 보관한다. 실행 전 콘텐츠 편집을 멈추고 다른 벤치마크를 동시에 실행하지 않는다.

## 지원서에 사용할 때

사용 가능: "AI 코딩 도구를 활용해 화면에 표시되지 않는 요약 생성을 위한 반복 API 호출과 목록·개수의 중복 조회를 제거했다. 실제 Notion 데이터로 전후 각 10회 비교한 결과, 목록 10개 조회의 외부 요청을 12회에서 1회로 줄였으며 캐시를 제외한 조회 함수 중앙값은 928ms에서 336ms로 감소했다."

전체 페이지 로딩 64% 향상, 서버 비용 92% 절감, 대규모 트래픽에서 검증, 사용자가 직접 원인을 분석/구현했다고 바꾸면 근거 범위를 벗어난다. 이번 원인 조사·구현·측정은 사용자의 요청으로 Codex가 수행했다. 사용자가 직접 검토하거나 재현한 범위는 이후 사실에 맞게 추가한다.
